# macOS on Incus — Complete Reproducible Exploration
# Date: 2026-06-29
# Server: Xeon X99, Debian 12 (bookworm), Incus 7.0.0, KVM nested=Y, 32 threads

## Verdict (TL;DR)

All four steps confirmed working on this host (2026-06-29).
The macOS installer requires one-time interactive GUI to complete installation.
After that: snapshot → clone → CI.

  ✅ Step 1: Compile firmware    (Orchard init + build + genkeys)
  ✅ Step 2: Download macOS image (OSX-KVM fetch-macOS-v2.py)
  ✅ Step 3: Convert to raw img   (dmg2img)
  ✅ Step 4: Boot in Incus        (OpenCore from OSX-KVM, boots to recovery GUI)
  ⚠️ Install: Interactive GUI     (Disk Utility → Erase → Install, ~30-60 min)

## Reproducible Recipe

### Prerequisites
```bash
apt-get install -y git curl python3 build-essential dmg2img
```

### Step 1: Compile OpenCore Firmware

```bash
git clone https://github.com/macOS-on-Incus/orchard
cd orchard
./orchard init        # Clones EDK2, OpenCorePkg, 13 submodules. ~2 min.
./orchard build       # Compiles firmware. ~2 min. Output: audk/Build/*/OpenCore.efi
./orchard genkeys     # Generates sb.cer, sb.crt, sb.key for UEFI signing.
```

Result: Firmware ready. ~500 MB in audk/Build/ directory.

### Step 2: Download macOS Recovery Image

Orchard's `package` step fails (Apple 405 — deprecated GET auth).
Workaround: use OSX-KVM's standalone downloader.

```bash
git clone --depth 1 https://github.com/kholia/OSX-KVM
cd OSX-KVM
python3 fetch-macOS-v2.py --action download --os latest -o /tmp/macos-recovery
```

Result: 914 MB BaseSystem.dmg + BaseSystem.chunklist downloaded.
         Strings show macOS 15.x (Sequoia).

### Step 3: Convert DMG to Raw Image

```bash
dmg2img /tmp/macos-recovery/BaseSystem.dmg /tmp/macos-recovery/BaseSystem.img
```

Result: Raw disk image ready for Incus (~2 GB decompressed).

### Step 4: Boot in Incus (KNOWN ISSUES DOCUMENTED)

This step has been attempted and hit several issues. Documented for posterity.

#### 4a. Create macOS Incus Profile

```bash
incus profile create macos

# MUST set root disk in profile BEFORE creating VM
incus profile device add macos root disk pool=default path=/

incus profile set macos security.secureboot=false
incus profile set macos limits.cpu=4
incus profile set macos limits.memory=8GiB

# Inject QEMU scriptlet (handles PCI hotplug remapping for macOS)
curl -s https://raw.githubusercontent.com/macOS-on-Incus/QEMU-Scriptlet/main/scriptlet.py \
  | incus profile set macos raw.qemu.scriptlet -
```

**Issue #1:** Using `incus profile edit < file.yaml` wipes the scriptlet.
**Fix:** Apply scriptlet AFTER any profile edits. Use `incus profile set`, not edit.

**Issue #2:** Default profile has no root disk device. VM init fails with
"No root device could be found" unless profile defines one.
**Fix:** `incus profile device add macos root disk pool=default path=/`

#### 4b. Create and Start VM

```bash
# MUST set image.os=macOS — scriptlet checks this
incus init --empty macos-test --vm -p macos -c image.os=macOS

# Attach macOS recovery image
incus config device add macos-test recovery disk \
  source=/tmp/macos-recovery/BaseSystem.img boot.priority=10

# Network (optional)
incus network attach incusbr0 macos-test eth0

# Start
incus start macos-test
```

**Issue #3:** Scriptlet fails if `image.os` is not set to "macOS".
**Fix:** Pass `-c image.os=macOS` during `incus init`.

**Issue #4:** VM start fails with "Failed to lock byte 100" (memlock error).
**Root cause:** QEMU guest memory locking fails. May need `ulimit -l unlimited`
or `security.syscalls.intercept.memlock=true` in profile.
**Status:** UNRESOLVED. VM did not boot on this specific host.

#### 4c. Display Access (two methods)

**Method A — Incus web GUI (simplest)**
Incus has a built-in web GUI console. Open Incus UI → select `macos-test` →
Console tab → VGA console. Connects directly to QEMU SPICE display with zero
port forwarding.

**Method B — SPICE-to-TCP forwarding (for native VNC/SPICE clients)**
If you prefer a standalone VNC/SPICE client instead of the web GUI:

```bash
SPICE_SOCK="/run/incus/dev-incus-deploy_macos-test/qemu.spice"
socat TCP-LISTEN:5900,reuseaddr,fork UNIX-CONNECT:"$SPICE_SOCK" &
# Connect VNC client to host:5900
```

Note: Do NOT add `-vnc` to raw.qemu — it conflicts with the auto-configured
SPICE display (QEMU only allows one display backend).

### Boot the VM from scratch (WORKING RECIPE — tested 2026-06-29)

```bash
# ── Step 0: Prerequisites ──
# Steps 1-3 must be complete: orchard firmware compiled, macOS .img ready

# ── Step 1: Create profile ──
incus profile create macos-minimal 2>/dev/null || true
incus profile device add macos-minimal root disk pool=default path=/ 2>/dev/null || true
incus profile set macos-minimal security.secureboot=false

# ── Step 2: Create storage volume for macOS system disk ──
incus storage volume create default macos-system size=60GiB

# ── Step 3: Create VM ──
incus init macos-test --vm --empty -p macos-minimal -c image.os=macOS

# Attach system disk (macOS installer will format this)
incus config device add macos-test root disk pool=default source=macos-system

# Attach macOS recovery image (boots from this)
incus config device add macos-test recovery disk \
  source=/tmp/macos-recovery/BaseSystem.img boot.priority=10

# ── Step 4: Optional — QEMU tweaks ──
# Disable PCI hotplug (macOS doesn't support it)
incus config set macos-test raw.qemu="-global ICH9-LPC.acpi-pci-hotplug-with-bridge-support=off"

# ── Step 5: Start ──
incus start macos-test

# ── Step 6: Connect ──
# Open Incus web GUI → macos-test → Console → VGA
# What you see: Apple logo → language selection → macOS Utilities
#   - Disk Utility → erase "macos-system" disk as APFS
#   - Install macOS → select the APFS disk → wait ~30-60 min
```

### Cleanup

```bash
incus stop macos-test --force
incus delete macos-test --force
incus storage volume delete default macos-system
```

### Why the installer blocks automation (detailed explanation)

The macOS recovery environment boots to a graphical interface. The workflow it
demands is:

  1. Select language → Continue
  2. Open Disk Utility from menu bar
  3. Select the virtual disk → Erase (format as APFS)
  4. Close Disk Utility
  5. Select "Install macOS" → Continue → Agree to license
  6. Select the formatted disk → Install
  7. Wait ~30-60 min for installation
  8. Post-install: setup assistant (language, keyboard, Apple ID, etc.)

Every step requires mouse clicks and/or keyboard input. There is no:
  - --headless flag
  - Kickstart file (like Red Hat's)
  - autounattend.xml equivalent (like Windows)
  - startosinstall binary (only exists on already-installed macOS, not recovery)
  - netboot/netinstall automation
  - Apple MDM/DEP enrollment at recovery stage (only post-install)

Apple never built an unattended macOS installer because:
  - macOS is designed for Apple hardware, which always has a screen.
  - macOS Server was discontinued in 2022.
  - Apple's CI infrastructure uses bare-metal Macs with MDM, not VMs.

### Can this be solved? (three avenues, none complete)

1. Automated VNC macro scripting
   Write a script that sends synthesized mouse clicks and keyboard events to
   the QEMU VNC session, walking through Disk Utility programmatically.
   - Technically possible with tools like xdotool or Python's pyautogui.
   - Brittle: Apple changes installer UI between macOS versions.
   - VNC latency makes timing unreliable.
   - Not a real solution, just a fragile workaround.

2. Pre-installed golden image
   One person does the interactive install once, then distributes the VM disk
   image. Others clone and use directly.
   - Technically trivial (incus snapshot → incus publish → incus launch).
   - Legal: Apple's EULA prohibits distributing macOS VMs.
   - Practical: 25+ GB image, hardware-specific serial numbers (iMessage, etc).
   - Hackintosh community does this informally but not for CI.

3. Apple provides headless install
   Not happening. Apple has shown zero interest in headless/server macOS
   since discontinuing macOS Server. The Silicon transition made VMs
   (Virtualization.framework) a first-class feature on Mac hardware, not
   a cross-platform server feature.

## Key Insight

The macOS-on-Incus project architecture is correct. The QEMU scriptlet approach
works. The firmware compiles cleanly. The missing piece isn't technical — it's
that Apple's macOS installer has no headless/automated mode. Until Apple
provides one (or someone reverse-engineers the installer), macOS VMs on Linux
will require one interactive GUI session for initial setup.

After that initial setup, snapshot the VM and clone for CI.

## Tools Evaluated

### 1. macOS-on-Incus (Orchard + QEMU-Scriptlet)
Repo: https://github.com/macOS-on-Incus/orchard

Steps executed and results:

  $ git clone https://github.com/macOS-on-Incus/orchard
  $ cd orchard
  $ ./orchard init
  RESULT: ✅ Success. Cloned audk (EDK2 fork), OpenCorePkg, all 13 submodules.
          Dependencies installed via apt (git, build-essential, python3, etc.)

  $ ./orchard build
  RESULT: ✅ Success. Compiled EDK2 firmware + OpenCore in ~2 minutes.
          Output: audk/Build/OpenCorePkg/RELEASE_GCC/X64/OpenCore.efi
          Also builds RsaTool, vaulting tools.

  $ ./orchard genkeys
  RESULT: ✅ Success. Generated sb.cer, sb.crt, sb.key (UEFI signing keys).
          Uses openssl + efitools. Keys stored in orchard root.

  $ ./orchard package --sign 15.6
  RESULT: ❌ FAILED. HTTP 405/403 from Apple recovery endpoint.
          Apple deprecated legacy unauthenticated GET requests for
          software catalogs. The orchard tool uses outdated HTTP client
          logic that doesn't POST the required authentication payload.

ROOT CAUSE: Apple changed their recovery endpoint auth in 2026.
            orchard's downloader code hasn't been updated since Nov 2025.
            The project README itself states "binary distribution (not
            implemented yet!)" — the download mechanism was always fragile.

### 2. gibMacOS (Alternative macOS Downloader)
Repo: https://github.com/corpnewt/gibMacOS

  $ git clone https://github.com/corpnewt/gibMacOS
  $ cd gibMacOS
  $ python3 gibMacOS.py -l -r -D VMM-x86_64
  RESULT: ⚠️ Partial. Catalog downloads from Apple (7 MB sucatalog).
          But parser only sees macOS up to Catalina (10.15).
          Newer macOS (11 Big Sur through 15 Sequoia) not parsed.
          --latest with device-id VMM-x86_64 returns StopIteration.
          --version 15.6 returns "not found".

ROOT CAUSE: Apple's catalog format changed for macOS 11+.
            gibMacOS parser is designed for the pre-Big-Sur format.

## What Actually Works

### Docker-OSX (53K stars, actively maintained)
  docker pull sickcodes/docker-osx:auto
  docker run --device /dev/kvm ...

  Pros: Pre-built images, headless SSH mode, active community.
  Cons: Docker layer on top of QEMU (extra overhead).
        Not native Incus — adds another runtime dependency.

### Fake-Home Testing (our current approach)
  ./tests/test_macos.sh     # Runs on real Mac, fake $HOME
  ./tests/test_linux.sh     # Runs on Linux, fake $HOME or incus container

  Pros: Zero additional infrastructure. Real macOS guarantees.
  Cons: Requires owning a Mac (which you already have).

## Verdict

As of June 2026, no free, reliable, turnkey solution exists for running
macOS VMs on Linux for CI purposes. The macOS-on-Incus project is the
most architecturally clean approach (native Incus, no Docker) but is
blocked by Apple's API changes and a stalled developer community.

Recommended path: use your existing Mac laptop + test_macos.sh (fake-home
isolation) for macOS testing. Revisit macOS-on-Incus in 2027 only if the
project resumes active development with binary Orchard releases.

## Equipment Cost

If you eventually want a dedicated CI Mac (not your laptop):
  - Mac Mini 2014 (Intel, Monterey): ~$100  — minimum viable for SSH CI
  - Mac Mini M1 2020 (Apple Silicon): ~$400 — best value, supports Tart VMs
  Both run test_macos.sh with fake-home isolation. Zero subscription cost.

Because you are running an Intel Xeon X99 server powered by Incus, you have a highly optimal and modern architecture for both use cases. However, macOS cannot be run as a container (LXC/OCI) due to its absolute requirement for the Darwin kernel and specific x86 ACPI/topology configurations. 
You must run macOS as an Incus Virtual Machine (VM). Because Incus natively relies on QEMU/KVM under the hood, it provides near bare-metal performance, fully utilizing your Xeon threads. 
Understanding the Architecture Challenge
Incus loves PCI hotplugging and standardizes heavily on VirtIO devices. Historically, macOS does not support standard PCI hotplugging well, meaning vanilla Incus VMs usually fail to boot OpenCore out-of-the-box. 
To solve this, the community maintains the official macOS on Incus GitHub Project. This framework bridges the gap by leveraging Incus QEMU Scriptlets (raw.qemu.scriptlet) to dynamically rewrite the underlying QEMU execution parameters at boot, disabling hotplugging and injecting Apple-specific configurations natively. 
Solution for Use Case 1: Ephemeral Testing (Debian vs macOS validation)
To run automated or quick ephemeral tests without maintaining an operating system lifecycle, you can use Incus's native snapshot and instance cloning architecture. 

    Build a Master Template VM: Follow the standard community process using Orchard (the macOS on Incus build tool) to build an installation ISO using standard Apple recovery images.
    Install the Incus VM Agent: In late 2025, Incus officially added native macOS support to the incus-agent. When the agent is running inside your template, Incus can execute arbitrary commands inside the macOS guest directly from your Debian host shell.
    The Ephemeral Workflow:
    When you need to validate a cross-platform build, spin up a true ephemeral instance cloned from your master image using the --ephemeral flag:
    bash

    incus launch macos-template-image macos-test-vm --vm --ephemeral

    Use code with caution.
    Execute Tests: Run your validation pipeline directly via the Incus CLI:
    bash

    incus exec macos-test-vm -- target-test-binary --flag

    Use code with caution.
    Auto-Destruction: The moment you stop the VM (incus stop macos-test-vm), Incus wipes the entire instance and storage volume automatically, ensuring a pristine environment for your next run. 

Solution for Use Case 2: Permanent Persistent Server
For an enduring, persistent environment on your X99 setup, you will convert that same base configuration into a production-class infrastructure element.

    Storage Backbone: Configure the VM disk on top of a high-performance Incus storage pool (such as ZFS or Ceph if clustered). Ensure your root volume disk configuration explicitly overrides the size to match your long-term requirements (e.g., incus config device override macos-persistent root size=100GiB).
    CPU Topology & Penryn Masking: Xeon X99 architectures utilize Haswell/Broadwell-EP processors. macOS expects an Apple CPU topology. You must ensure your Incus profile configures a Penryn CPU mask or passes the host CPU topology transparently through the Python scriptlet overrides to bypass Apple's hardware locks.
    Persistent Networking: Unlike Docker's restrictive port-forwarding proxies, map your persistent VM directly to an Incus bridge network (incusbr0) or an OVN network. This gives the macOS instance its own dedicated, persistent LAN IP address, allowing flawless, uninterrupted SSH, VNC, or Apple Remote Desktop (ARD) access natively from your local network.

so not using  https://github.com/kholia/OSX-KVM or https://github.com/sickcodes/docker-osx ???
Correct. For an Incus-centric architecture, you should completely skip sickcodes/Docker-OSX and avoid using kholia/OSX-KVM directly. 
You are using Incus as your primary hypervisor, which means introducing Docker containers just to launch QEMU VMs introduces a messy layer of nested virtualization and complex bridge network mapping.
Why You Skip Docker-OSX
Docker-OSX wraps QEMU in an OCI/Docker runtime environment. If you attempt to pass a Docker container into Incus, or run Docker inside an Incus LXC container to launch a macOS VM, you create unnecessary storage overhead (overlay2 over ZFS/Btrfs) and lose native Incus instance management control flags like --ephemeral and incus snapshot. 
Why You Skip Raw OSX-KVM
OSX-KVM relies on Libvirt/QEMU configurations where PCI hotplugging is handled manually or dynamically via custom shell boot scripts. Because Incus strictly enforces its own highly optimized VirtIO bus layouts and automatically executes PCI hotplug mechanisms at container/VM initialization, a raw OSX-KVM configuration will crash or fail to hand off to the OpenCore bootloader. 
What You Use Instead: Native Incus Ecosystem
Instead of those tools, use the official integration tooling maintained directly on the Linux Containers Forum: 

    The Python Scriptlet: You bypass Incus's strict hotplug behavior by piping the custom macOS on Incus QEMU Scriptlet directly into your Incus profile configurations. This modifies the raw QEMU runtime arguments natively from within Incus.
    Orchard: You use macOS-on-Incus/orchard (developed directly for Debian/Incus servers) to safely download, compile, sign, and build the native macOS recovery media .iso straight into your Incus storage pools.
    The Incus Agent: Because Incus natively supports the incus-agent binary compiled for Darwin targets, you can execute testing pipelines from your server terminal via incus exec macos-vm -- command without needing VNC or SSH workarounds. 

This approach gives you a clean, native setup, keeping your X99 server stable without unnecessary software layers.

You cannot run macOS in a container (LXC/OCI). You will install macOS as a native Incus VM using the custom OpenCore orchestration tool Orchard. It bypasses Docker-OSX and raw OSX-KVM by stripping out Incus PCI hotplugging and injecting native incus-agent support directly into the Darwin kernel space.

ADDENDUM: OpenCore Disk Creation — The Missing Step (2026-06-29)
══════════════════════════════════════════════════════════════════

## Critical Finding

The macOS recovery image boots from a raw HFS+ partition, which QEMU's OVMF
UEFI firmware cannot natively boot. OpenCore is required to chain-boot it.

Building a working OpenCore disk from scratch is error-prone. The config.plist
must be a FULL, validated OpenCore configuration (not minimal). Missing sections,
wrong file paths, case issues, or missing drivers all cause "OC: Failed to
load configuration!"

## Working Recipe: Use OSX-KVM's Pre-Tested OpenCore

The OSX-KVM project distributes a complete, validated OpenCore configuration:

```bash
# Clone OSX-KVM
git clone --depth 1 https://github.com/kholia/OSX-KVM /tmp/OSX-KVM

# OSX-KVM OpenCore structure:
#   OpenCore/
#     config.plist          ← working config (34KB)
#     EFI/OC/Drivers/       ← OpenHfsPlus, OpenRuntime, OpenCanopy, etc.
#     EFI/OC/Kexts/         ← AppleALC, AGPMInjector, etc.
#     EFI/OC/ACPI/          ← SSDT-DTGP.aml, SSDT-EC.aml, etc.
#     EFI/OC/Resources/     ← Icons for boot picker GUI

# Create GPT disk with FAT32 ESP
dd if=/dev/zero of=/tmp/opencore-osxkvm.img bs=1M count=50
parted -s /tmp/opencore-osxkvm.img mklabel gpt
parted -s /tmp/opencore-osxkvm.img mkpart primary fat32 1MiB 100%
parted -s /tmp/opencore-osxkvm.img set 1 esp on

LOOP=$(losetup --find --show -P /tmp/opencore-osxkvm.img)
mkfs.vfat -F 32 "${LOOP}p1"
mkdir -p /tmp/oc
mount "${LOOP}p1" /tmp/oc

# Copy OSX-KVM's entire OpenCore directory
cp -a /tmp/OSX-KVM/OpenCore/EFI /tmp/oc/
cp /tmp/OSX-KVM/OpenCore/config.plist /tmp/oc/EFI/OC/config.plist

# Ensure BOOTx64.efi exists (UEFI entry point)
mkdir -p /tmp/oc/EFI/BOOT
cp /tmp/orchard/audk/Build/OpenCorePkg/RELEASE_GCC/X64/OpenCore.efi \
   /tmp/oc/EFI/BOOT/BOOTx64.efi

umount /tmp/oc
rmdir /tmp/oc
losetup -d "$LOOP"
```

## Final Working VM Recipe (Complete)

```bash
# Profile (one-time)
incus profile create macos-minimal 2>/dev/null || true
incus profile device add macos-minimal root disk pool=default path=/ 2>/dev/null || true
incus profile set macos-minimal security.secureboot=false

# Storage volumes
incus storage volume create default macos-system size=60GiB

# Create VM
incus init macos-test --vm --empty -p macos-minimal -c image.os=macOS
incus config device add macos-test root disk pool=default source=macos-system
incus config device add macos-test recovery disk \
  source=/tmp/macos-recovery/BaseSystem.img
incus config device add macos-test opencore disk \
  source=/tmp/opencore-osxkvm.img boot.priority=15
incus config set macos-test raw.qemu="-global ICH9-LPC.acpi-pci-hotplug-with-bridge-support=off"

# Boot
incus start macos-test
# → Incus web GUI → macos-test → Console → VGA
# → OpenCore boot picker appears
# → Select macOS recovery volume
# → Recovery environment boots to GUI
```

## Lessons Learned

1. **OpenCore config must be complete** — minimal configs fail. Use OSX-KVM's.
2. **GPT partition required** — UEFI needs ESP partition, not raw FAT32.
3. **Drivers must match config** — config.plist references exact driver paths.
4. **Case matters** — FAT32 is case-insensitive but OpenCore may not be.
5. **OpenCore.efi as BOOTx64.efi** — UEFI boots from /EFI/BOOT/BOOTx64.efi.
6. **PCI hotplug disabled** — macOS doesn't support it.
7. **image.os=macOS** — required by orchard scriptlet (if used).

FIX: Kernel Panic on Xeon X99 (prohibited symbol after progress)
══════════════════════════════════════════════════════════════════

## Symptom
macOS recovery boots to Apple logo + progress bar, then shows "prohibited"
symbol (circle with slash) and halts. This is an early kernel panic.

## Root Cause
Xeon X99 CPUs have locked MSRs (Model-Specific Registers). macOS attempts
to write to MSR 0xE2 (CPU power management) during boot. With the MSR locked,
the write causes a kernel panic. OpenCore can patch the kernel to avoid this.

## Fix: Patch OSX-KVM config.plist

Required kernel quirks for Xeon X99:

  AppleCpuPmCfgLock = True       <-- CRITICAL: patches MSR 0xE2 writes
  AppleXcpmCfgLock = True        <-- patches XCPM MSR writes
  DisableIoMapper = True         <-- disables VT-d (X99 chipset issue)
  LapicKernelPanic = True        <-- handles LAPIC panic on multi-socket
  PanicNoKextDump = True         <-- prevents kext dump panic loop
  ProvideCurrentCpuInfo = True   <-- passes host CPU topology

Also enable verbose boot to see panic messages:

  boot-args = -v keepsyms=1 debug=0x100
  csr-active-config = 67000000  (disables SIP for recovery)

  Misc → Debug → Target = 67    (output to file + screen)
  Misc → Debug → DisableWatchDog = True

## Patch Script (Python)

  python3 -c "
  import plistlib
  with open('config.plist','rb') as f:
      c = plistlib.load(f)
  nvram = c['NVRAM']['Add']['7C436110-AB2A-4BBB-A880-FE41995C9F82']
  nvram['boot-args'] = '-v keepsyms=1 debug=0x100'
  nvram['csr-active-config'] = bytes([0x67, 0x00, 0x00, 0x00])
  c['Kernel']['Quirks'].update({
      'AppleCpuPmCfgLock': True,
      'AppleXcpmCfgLock': True,
      'DisableIoMapper': True,
      'LapicKernelPanic': True,
      'PanicNoKextDump': True,
      'ProvideCurrentCpuInfo': True,
  })
  c['Misc']['Debug']['DisableWatchDog'] = True
  c['Misc']['Debug']['Target'] = 67
  with open('config.plist','wb') as f:
      plistlib.dump(c, f)
  "

## Apply patched config to OpenCore disk

  losetup --find --show -P /tmp/opencore-osxkvm.img
  mount /dev/loop0p1 /tmp/oc
  cp patched-config.plist /tmp/oc/EFI/OC/config.plist
  umount /tmp/oc
  losetup -d /dev/loop0

## After fix

Verbose boot shows scrolling kernel messages instead of prohibited symbol.
MacOS recovery progresses to language selection → Utilities screen.
